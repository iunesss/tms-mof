# نظام إدارة التدريب والدورات (TMS–MOF)

نظام ويب متكامل لإدارة الدورات التدريبية والمهام، بدءًا من إنشاء الدورة وتوزيع دعوات الترشيح، مرورًا بمراجعة الترشيحات والمستندات، ووصولًا إلى تأكيد المشاركين وإكمال الدورة وأرشفتها مع التقرير النهائي.

## التقنيات المستخدمة

- الواجهة الأمامية: Vite، JavaScript، HTML، Tailwind CSS.
- الخادم: Node.js، Express.
- قاعدة البيانات: MySQL باستخدام `mysql2`.
- المصادقة: JWT محفوظ في Cookie آمنة.
- التحقق من البيانات: Zod.
- رفع الملفات: Multer.
- الحماية: Helmet، CORS، Rate Limiting، وتحديد الصلاحيات حسب الدور.
- الاختبارات: Node.js Test Runner، فحوصات واجهات، ESLint، وVite Build.

## أدوار النظام

| الدور | المسؤوليات الرئيسية |
| --- | --- |
| `SUPER_ADMIN` | إدارة المستخدمين والدورات والتقارير ومتابعة النظام كاملًا. |
| `COURSE_MANAGER` | إنشاء الدورات وإدارتها، اختيار المرشحين، مراجعة المستندات، وإغلاق الدورة. |
| `AGENT` | مراجعة واعتماد أو رفض ترشيحات الأقسام التابعة لقطاعه. |
| `DEPARTMENT_MANAGER` | ترشيح موظفي القسم للدورات الموجهة إلى قسمه. |
| `EMPLOYEE` | متابعة الدورة، تنزيل النماذج، رفع النسخ المعبأة، واستلام المستندات والإشعارات. |

## سير العمل الرئيسي

1. ينشئ المسؤول أو مدير الدورات دورة أو مهمة ويحدد المقاعد والجهات المستهدفة والنماذج المطلوبة.
2. يرشح مدير القسم الموظفين قبل انتهاء موعد الترشيح.
3. يراجع وكيل القطاع الترشيحات ويرفع المقبولين إلى إدارة الدورة.
4. يختار مدير الدورة المرشحين النهائيين ضمن الحدود المتاحة؛ عندها ينتقل الموظف إلى مسار المرشح.
5. يرفع الموظف النماذج والمستندات المطلوبة، ثم يراجعها المسؤول المخول ويعتمدها أو يطلب إعادة رفعها مع السبب.
6. لا يسمح بالقبول المبدئي أو التأكيد إلا بعد استيفاء المتطلبات المحددة في الخادم.
7. يمكن إرسال مستندات مثل التأشيرة والتذكرة والخطاب الرسمي إلى الموظف مع إشعار.
8. بعد اكتمال الدورة تتحول إلى `COMPLETED`، ثم تُؤرشف فقط بعد رفع التقرير النهائي.
9. تحفظ العمليات المهمة في سجل التدقيق، وتصل الإشعارات إلى الأطراف المعنية عند تغير الحالات.

## معالجة طلب API

يمر الطلب عادة بهذا الترتيب:

```text
Browser → Route → Authentication → Authorization → Validation/Upload
        → Controller → Service/Repository → MySQL → JSON Response
```

- `authenticate` يتحقق من جلسة المستخدم ويضع بياناته في `req.user`.
- `authorize` يمنع أي دور غير مصرح له من تنفيذ العملية.
- طبقة التحقق ترفض البيانات الخاطئة قبل وصولها إلى منطق العمل.
- المتحكم يبقى خفيفًا: يستقبل الطلب ويستدعي العملية المناسبة ويرسل النتيجة.
- العمليات الحساسة تستخدم معاملات قاعدة البيانات لضمان تنفيذ جميع الخطوات أو التراجع عنها كاملة.

## التجهيز لأول مرة

المتطلبات:

- Node.js حديث.
- MySQL وقاعدة بيانات المشروع جاهزة.
- npm.

ثبّت الحزم من جذر المشروع:

```bash
npm install
npm --prefix backend install
```

انسخ ملف البيئة النموذجي:

```bash
copy backend\.env.example backend\.env
```

على macOS أو Linux:

```bash
cp backend/.env.example backend/.env
```

ثم حدّث قيم قاعدة البيانات و`JWT_SECRET` داخل `backend/.env`. لا ترفع هذا الملف إلى Git.

## نقاط API الرئيسية

جميع النقاط تبدأ بـ `/api`:

- `/api/auth`: تسجيل الدخول والخروج والجلسة.
- `/api/dashboard`: لوحة التحكم، وتُحدد النتيجة حسب دور المستخدم.
- `/api/courses`: الدورات والترشيحات والمرشحون والمستندات.
- `/api/notifications`: إشعارات المستخدم الحالي.
- `/api/profile`: الملف الشخصي والمستندات الشخصية.
- `/api/users`: إدارة المستخدمين وفق الصلاحية.
- `/api/reports`: التقارير والأرشيف.

الواجهة تستخدم Vite Proxy أثناء التطوير، لذلك تستدعي `/api/...` و`/uploads/...` دون تثبيت عنوان الخادم داخل JavaScript.

## تخزين الملفات

جميع الملفات المرفوعة تحفظ داخل:

```text
backend/public/uploads/
```

وتقسم إلى مجلدات بحسب النوع، مثل الدورات والنماذج والملفات الشخصية والتقارير ومرفقات المرشحين. محتوى هذا المجلد بيانات تشغيل وليس شفرة مصدر، ولذلك هو مستبعد من Git، بينما يحافظ `.gitkeep` على وجود المجلد بعد استنساخ المشروع.

في الإنتاج يجب استخدام تخزين دائم أو Object Storage مع نسخ احتياطية، وعدم الاعتماد على Git لحفظ ملفات المستخدمين.

## الفحص والاختبارات

نفّذ الأوامر التالية من جذر المشروع:

```bash
npm run lint
npm run check:frontend
npm --prefix backend test
npm run build
```

- `lint`: يفحص جودة ملفات JavaScript.
- `check:frontend`: يفحص صفحات الواجهة والروابط والملفات المرتبطة بها.
- اختبار الخادم: يغطي المصادقة والمسارات والتحقق والرفع ودورة حياة المرشح والدورة.
- `build`: يتأكد أن جميع صفحات Vite قابلة للبناء للإنتاج.

توجد اختبارات Smoke داخل `backend/scripts`. بعضها يتصل بقاعدة البيانات الفعلية، لذلك يجب قراءة الملف والتأكد من بيئة الاختبار قبل تشغيل أي اختبار يكتب بيانات.

## الحماية

- كلمات المرور تخزن بعد تشفيرها بـ bcrypt وليست كنص صريح.
- JWT يستخدم Cookie وتتحقق منه طبقة المصادقة.
- الصلاحيات تطبق في الخادم ولا تعتمد على إخفاء الأزرار في الواجهة.
- محاولات الدخول الخاطئة تخضع لـRate Limiting، ولا تحتسب عملية الدخول الناجحة كفشل.
- Helmet يضيف ترويسات حماية، وCORS يقصر الاتصال على أصل الواجهة المحدد.
- Zod يتحقق من المدخلات، وMulter يفرض نوع الملف وحجمه ومسار تخزينه.
- ملفات البيئة، إعداد Codex المحلي، وملفات المستخدمين المرفوعة مستبعدة من Git.

## ملاحظات Git

لا يجب رفع العناصر التالية:

- `backend/.env` أو أي ملف يحتوي أسرارًا.
- `.codex/` لأنه إعداد محلي لأداة التطوير.
- محتويات `backend/public/uploads/` لأنها ملفات تشغيل خاصة بالمستخدمين.
- `node_modules/` و`dist/` لأنها قابلة لإعادة الإنشاء.

أما `scripts/` و`backend/test/` و`eslint.config.js` فهي جزء مهم من المشروع ويجب الاحتفاظ بها في المستودع لأنها مسؤولة عن التشغيل والفحص والاختبارات.

## البناء للإنتاج

```bash
npm run build
npm --prefix backend start
```

ينتج بناء الواجهة داخل `dist/`. عند النشر يجب ضبط متغيرات البيئة الفعلية، استخدام HTTPS، تأمين قاعدة البيانات، توفير تخزين دائم للمرفقات، وتشغيل الخادم بواسطة مدير عمليات مناسب.
